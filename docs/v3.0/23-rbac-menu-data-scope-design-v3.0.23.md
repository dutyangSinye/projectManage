# 角色、菜单与数据访问范围设计

- 版本：v3.0.23
- 日期：2026-09-01
- 状态：已实现，已发布
- 适用系统：综合项目管理系统

## 1. 摘要

当前系统把管理权限直接存放在用户记录中，每个用户一组 `can_manage_*` 字段，再附带一个全局项目数据范围。这种方式适合早期验证，但当系统继续增加合同、收付款、客户、供应商、项目看板和系统管理菜单时，配置会越来越难维护，也无法清晰表达“同一个人可以管理哪些菜单、能执行哪些操作、能看哪些数据”。

本方案升级为 RBAC + 数据范围：用户通过飞书组织身份进入系统，用户绑定一个或多个角色，角色配置菜单和操作权限，角色授权关系配置数据访问范围。系统最终按“用户有效角色 → 菜单查看权限 → 操作权限 → 数据范围 → 字段脱敏”顺序判断访问结果。

## 2. 目标与边界

### 2.1 目标

| 目标 | 验收结果 |
| --- | --- |
| 角色复用 | 新增人员只需分配角色，不重复逐项勾选权限 |
| 菜单可控 | 没有菜单查看权限的用户不显示菜单，直接访问路由返回 403 |
| 操作可控 | 查看、新增、编辑、删除、审批、导出、同步等操作可以分别授权 |
| 数据可控 | 同一菜单下可以限制为本人、负责项目、部门及下级、全部数据 |
| 权限可解释 | 管理员能看到某个用户的最终权限来自哪个角色、覆盖哪些数据 |
| 平滑迁移 | 现有管理员和系统管理员权限不因升级丢失，旧配置可核对后再下线 |

### 2.2 本期不做

- 不接入飞书租户级角色体系，飞书只作为人员和部门来源。
- 不做复杂的拒绝权限；首版采用“允许权限并集”，避免角色互相覆盖导致难以排查。
- 不做字段级自由配置编辑器；敏感字段采用系统内置规则和少量固定权限。
- 不做项目级逐条授权作为首版默认模式，保留 `CUSTOM_PROJECT` 扩展位。

## 3. 权限模型

### 3.1 四个对象

```text
飞书用户
   │ 多对多
   ▼
角色 ──────── 菜单权限 + 操作权限
   │
   └──────── 授权数据范围
                    │
                    ▼
             最终可见数据和字段
```

1. **用户**：来自飞书组织架构的人员，不在本系统重复维护姓名和部门。
2. **角色**：可复用的权限模板，例如项目负责人、出纳、工时管理员、项目经营查看者。
3. **菜单/操作权限**：控制能否看到模块和执行具体动作。
4. **数据范围**：控制允许访问的项目、工时、合同、收付款、客户供应商或人员成本记录。

### 3.2 权限粒度

每个菜单资源至少支持以下操作码：

| 操作码 | 含义 | 示例 |
| --- | --- | --- |
| `VIEW` | 查看列表、详情和摘要 | 查看项目合同 |
| `CREATE` | 新增 | 新增合同、合同收款单 |
| `EDIT` | 修改草稿或主数据 | 编辑项目 |
| `DELETE` | 删除、停用或作废 | 删除客户 |
| `APPROVE` | 审批或确认 | 出纳审批合同付款单 |
| `EXPORT` | 导出明细 | 导出工时台账 |
| `SYNC` | 同步外部组织或数据 | 同步飞书组织架构 |
| `CONFIGURE` | 修改系统配置 | 修改通知策略 |

权限判断采用默认拒绝：没有 `VIEW` 不能进入页面，没有对应操作码不能显示或调用操作接口。后端接口必须再次校验，前端隐藏不作为安全措施。

### 3.3 角色并集规则

- 一个用户可以绑定多个角色。
- 菜单和操作权限取所有有效角色的并集。
- 数据范围取所有角色中最大的可见范围：`ALL` > `DEPARTMENT_AND_CHILDREN` > `OWNED_PROJECTS` > `SELF`。
- 审批待办是例外：用户被指定为该单据的审批人时，可以看到分配给自己的待办，不受项目列表范围缩小影响。
- 系统管理员是最高权限，具备所有菜单、操作、全部数据和权限配置能力，不能被普通管理员移除。

这种并集规则容易解释，但也意味着给用户增加一个“全部项目”角色后，其数据范围会扩大。授权保存前必须展示影响提示。

## 4. 数据范围设计

### 4.1 范围类型

| 范围编码 | 名称 | 规则 |
| --- | --- | --- |
| `SELF` | 仅本人 | 只能查看当前用户自己的工时、自己提交的单据或个人成本 |
| `OWNED_PROJECTS` | 负责项目 | 项目负责人是当前用户的项目及其合同、阶段、收付款、经营数据 |
| `DEPARTMENT_AND_CHILDREN` | 本部门及下级 | 项目所属部门属于选定部门树及其下级部门 |
| `ALL` | 全部数据 | 所有业务数据，只有明确授权的角色或系统管理员可使用 |
| `CUSTOM_DEPARTMENTS` | 指定部门树 | 选定一个或多个部门及其下级部门，作为后续扩展 |
| `CUSTOM_PROJECTS` | 指定项目 | 选定项目清单，作为后续扩展，不纳入首版必需流程 |

首版界面先开放 `SELF`、`OWNED_PROJECTS`、`DEPARTMENT_AND_CHILDREN`、`ALL`。部门选择使用飞书组织树，选择父部门默认包含所有下级部门。

### 4.2 资源与范围映射

| 资源 | `SELF` | `OWNED_PROJECTS` | 部门及下级 | `ALL` |
| --- | --- | --- | --- | --- |
| 项目 | 本人负责项目 | 本人负责项目 | 部门项目 | 全部项目 |
| 合同/阶段 | 本人负责项目下 | 本人负责项目下 | 部门项目下 | 全部 |
| 收款/付款 | 本人提交或本人负责项目下 | 负责项目下 | 部门项目下 | 全部 |
| 项目看板 | 本人负责项目 | 本人负责项目 | 部门项目 | 全部 |
| 工时台账 | 本人记录 | 负责项目的工时 | 部门项目的工时 | 全部工时 |
| 人员成本 | 本人 | 负责项目成员的成本 | 部门及下级人员 | 全部人员 |
| 客户/供应商 | 关联到可见项目的记录 | 关联到可见项目的记录 | 关联到可见项目的记录 | 全部 |
| 组织同步/基础配置/权限 | 不适用，必须单独授权 | 不适用 | 不适用 | 仅管理员权限 |

合同收付款审批和工时审批优先按“分配给我的审批任务”查询；查看关联项目详情时再执行项目数据范围校验。没有审批权限的用户即使能看到列表，也不能执行审批操作。

### 4.3 字段保护

菜单和数据范围通过后，还要执行固定字段保护：

- 银行账号默认显示后四位；收付款新增、编辑和出纳审批期间按业务权限查看完整账号。
- 人员单天成本只对人员成本菜单授权用户开放。
- 管理员角色、授权关系和系统配置只对管理员管理/基础配置授权用户开放。
- 导出接口沿用列表数据范围和字段脱敏规则，不能通过导出绕过页面权限。

## 5. 初始菜单树与操作权限

```text
工作台
├─ 工作台概览                 VIEW
├─ 快捷发起工时/审批           按业务操作权限显示
└─ 项目负责人区                按项目数据范围显示

工时管理
├─ 我的工时                   VIEW / CREATE / EDIT
├─ 工时审批                   VIEW / APPROVE
├─ 工时看板                   VIEW / EXPORT
└─ 工时台账                   VIEW / EDIT / DELETE / EXPORT

项目管理
├─ 项目管理                   VIEW / CREATE / EDIT / DELETE
├─ 项目合同                   VIEW / CREATE / EDIT / DELETE
├─ 合同收款                   VIEW / CREATE / EDIT / DELETE
├─ 合同付款                   VIEW / CREATE / EDIT / DELETE
├─ 项目看板                   VIEW / EXPORT
├─ 供应商管理                 VIEW / CREATE / EDIT / DELETE
└─ 客户管理                   VIEW / CREATE / EDIT / DELETE

系统管理
├─ 人员成本                   VIEW / EDIT
├─ 集成与通知                 VIEW / CONFIGURE / SYNC / EXPORT
├─ 管理员管理                 VIEW / CONFIGURE
└─ 基础配置                   VIEW / CREATE / EDIT / DELETE
```

工作台、我的工时和本人审批是登录用户的基础能力，不需要把员工本人功能误配置成后台管理菜单。管理模块只显示用户拥有 `VIEW` 的菜单；项目详情、合同详情和单据详情沿用对应资源的 `VIEW` 权限及数据范围。

## 6. 建议的内置角色

内置角色可被复制生成自定义角色；系统内置角色不直接删除，只允许停用或复制。

| 角色 | 主要菜单 | 默认数据范围 |
| --- | --- | --- |
| 系统管理员 | 全部菜单和全部操作 | 全部数据 |
| 项目经营管理员 | 项目、合同、收付款、客户供应商、项目看板 | 全部项目，可按需收窄 |
| 项目负责人 | 项目详情、合同、收付款、项目看板 | 负责项目 |
| 出纳 | 合同收款、合同付款、合同收付款审批、单据详情 | 审批待办 + 授权项目范围 |
| 工时管理员 | 工时台账、工时看板 | 部门及下级或全部工时 |
| 工时审批人 | 工时审批 | 分配给自己的审批任务 |
| 人员成本管理员 | 人员成本 | 部门及下级人员 |
| 经营查看者 | 项目、合同、项目看板 | 部门及下级或全部项目，只读 |
| 集成管理员 | 集成与通知、组织同步 | 全组织配置，不开放财务数据 |

默认角色只是起点。管理员可以复制角色，例如“技术服务部经营查看者”，再把数据范围改为技术服务部及下级。

## 7. 管理员管理页面设计

### 7.1 页面布局

管理员管理从当前“人员一行勾选很多字段”改成三块：

```text
管理员管理
┌──────────────┬─────────────────────────────────────────────┐
│ 角色列表       │ 角色详情                                    │
│                │ [基本信息] [菜单与操作] [默认数据范围]        │
│ 系统管理员     │                                             │
│ 项目负责人     │ 菜单树                                      │
│ 出纳           │ ☑ 项目管理     查看 新增 编辑 删除            │
│ 工时管理员     │ ☑ 项目合同     查看 新增 编辑 删除            │
│ ...            │ ☐ 基础配置     查看 新增 编辑 删除            │
└──────────────┴─────────────────────────────────────────────┘

人员授权
┌─────────────────────────────────────────────────────────────┐
│ [选择飞书人员] [关键词] [状态]                         [查询] │
├──────┬────────┬──────────────┬──────────┬──────────┬─────────┤
│ 人员 │ 部门   │ 已分配角色    │ 数据范围 │ 状态     │ 操作    │
│ 杨阳 │ 产品研发部 │ 项目负责人 │ 负责项目 │ 启用     │ 编辑    │
└──────┴────────┴──────────────┴──────────┴──────────┴─────────┘
```

### 7.2 角色编辑

角色编辑弹窗/侧抽屉分三步：

1. **基本信息**：角色名称、编码、说明、启用状态。
2. **菜单与操作**：树形菜单，父级勾选为半选时表示只授权了部分子菜单；每个菜单下展示查看、新增、编辑、删除、审批、导出、同步、配置操作。
3. **默认数据范围**：选择范围类型；选择部门时出现组织树；显示“该范围会影响哪些菜单”。

保存前右侧显示权限摘要，例如：“可查看项目合同、项目收付款；范围为产品研发部及下级；不可查看系统配置”。

### 7.3 人员授权

人员授权只从飞书同步人员中选择，不允许手工输入姓名。一个人可以绑定多个角色，每条角色绑定可覆盖默认数据范围，但默认操作建议使用角色默认范围，减少误配。

授权详情展示：

- 人员、部门、飞书状态；
- 角色列表和每个角色的来源；
- 有效菜单和操作；
- 每个资源的最终数据范围；
- 最近修改人和修改时间；
- 权限变更前后对比。

### 7.4 有效权限预览

管理员选择任意已同步人员后，可以点击“查看生效权限”，看到最终结果，而不是只看到角色名称：

```text
杨阳的生效权限
项目合同       查看 / 新增 / 编辑       负责项目
合同付款       查看 / 新增              产品研发部及下级
项目看板       查看 / 导出              产品研发部及下级
基础配置       无权限
```

该页面同时提供“为什么能看到”：显示角色来源、部门范围来源和是否属于审批待办，便于处理权限争议。

## 8. 后端与数据设计

### 8.1 建议新增数据表

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `roles` | `id`, `code`, `name`, `description`, `is_builtin`, `is_active` | 角色主表 |
| `menus` | `id`, `code`, `parent_id`, `label`, `route`, `sort_order`, `is_active` | 菜单资源树 |
| `role_permissions` | `role_id`, `menu_id`, `actions` | 角色的菜单和操作权限 |
| `user_roles` | `user_id`, `role_id`, `is_active` | 用户与角色多对多关系 |
| `role_data_scopes` | `role_id`, `resource`, `scope_type`, `department_id` | 角色默认数据范围 |
| `user_role_scopes` | `user_id`, `role_id`, `resource`, `scope_type`, `department_id` | 人员对角色范围的覆盖 |
| `permission_audits` | `actor_id`, `target_user_id`, `role_id`, `before_json`, `after_json` | 权限变更审计 |

`actions` 可先使用 JSON 数组，后续权限稳定后再拆成关联表。部门范围必须存 ID，不存部门名称；查询时通过飞书同步的部门树计算下级部门。

### 8.2 有效权限计算

```text
current_user
  → 查询有效 user_roles
  → 合并 role_permissions
  → 合并 role_data_scopes / user_role_scopes
  → 生成 EffectivePermission
  → 菜单渲染、接口动作校验、数据查询条件、字段脱敏
```

后端提供统一的 `require_access(resource, action, project_id=None)` 方法。所有列表、详情、导出、附件和审批接口必须使用统一校验，不允许各接口继续自行读取旧的 `can_manage_*` 字段。

### 8.3 接口草案

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/roles` | 查询角色列表 |
| POST | `/api/v1/admin/roles` | 新增自定义角色 |
| GET/PATCH | `/api/v1/admin/roles/{id}` | 查看/修改角色基本信息 |
| DELETE | `/api/v1/admin/roles/{id}` | 停用自定义角色，内置角色不可物理删除 |
| GET | `/api/v1/admin/menus` | 查询菜单树和可用操作码 |
| GET/PATCH | `/api/v1/admin/roles/{id}/permissions` | 查询/保存角色权限 |
| GET | `/api/v1/admin/user-roles` | 查询人员授权列表 |
| PUT | `/api/v1/admin/users/{user_id}/roles` | 保存人员角色和范围覆盖 |
| GET | `/api/v1/admin/users/{user_id}/effective-permissions` | 查看最终权限预览 |
| GET | `/api/v1/auth/me/permissions` | 登录后返回前端菜单和操作权限 |

所有管理接口要求当前用户具备“管理员管理 / 权限配置”权限；系统管理员始终可用。接口错误统一返回 `403 PERMISSION_REQUIRED`、`403 DATA_SCOPE_REQUIRED`、`409 LAST_ADMIN_PROTECTED` 等可识别错误码。

## 9. 旧版权限清理方案

### 9.1 清理原则

本版本不迁移旧版逐用户权限。启动时直接清理旧版授权记录，管理员通过 RBAC 角色、菜单、操作和数据范围重新配置。旧数据库表结构暂时保留，但不再读取、不再提供接口、不再参与权限计算。

### 9.2 清理步骤

1. 写入固定菜单树和内置角色。
2. 保留环境变量 `SYSTEM_ADMIN_USER_IDS` 作为系统管理员最高权限兜底。
3. 删除 `MIGRATED_USER_*` 迁移角色及其角色权限、数据范围、人员授权。
4. 删除 `admin_permissions` 中的旧版逐用户权限记录。
5. 权限计算只读取 RBAC 有效角色，未重新授权的普通用户默认无管理菜单。

### 9.3 保护规则

- 至少保留一名系统管理员；不能通过页面清空最后一个管理员。
- 不能删除当前正在使用的角色；只能停用，停用前提示受影响人员。
- 停用角色后，用户的有效权限立即重新计算，已有审批任务不被删除。
- 飞书组织同步只更新用户和部门资料，不自动删除角色、授权或审计记录。

## 10. 核心流程

### 10.1 配置权限

```text
管理员进入管理员管理
  → 新建/选择角色
  → 配置菜单查看权限
  → 配置具体操作权限
  → 配置默认数据范围
  → 查看权限摘要和影响人数
  → 保存并写入权限审计
```

### 10.2 给人员授权

```text
选择飞书人员
  → 分配一个或多个角色
  → 检查角色并集和范围是否扩大
  → 必要时覆盖某个角色的数据范围
  → 查看生效权限预览
  → 保存
  → 下一次请求立即按新权限生效
```

### 10.3 用户访问业务页面

```text
飞书登录/当前会话
  → 获取有效权限
  → 无 VIEW：不显示菜单，路由/接口返回 403
  → 有 VIEW：进入页面
  → 点击操作：校验操作码
  → 查询数据：追加数据范围条件
  → 返回结果：执行字段脱敏
```

## 11. 测试与验收

### 功能验收

- 新建角色、编辑角色、停用角色、复制角色。
- 给用户绑定多个角色，验证权限并集。
- 验证角色默认范围和人员范围覆盖。
- 菜单无查看权限时不显示，直接输入 URL 返回 403。
- 无新增/编辑/删除/审批/导出权限时，按钮隐藏且接口返回 403。
- 上级部门范围包含下级部门，选择子部门不包含兄弟部门。
- 项目、合同、收付款、工时台账、人员成本和导出接口都按范围过滤。
- 工时审批和出纳审批只显示分配给自己的待办，并保留审批动作权限。
- 银行账号、人员成本和权限配置按字段保护规则展示。

### 迁移验收

- 旧管理员权限与迁移后有效权限逐人对比。
- 系统管理员可以访问全部菜单和数据。
- 普通员工不出现后台管理菜单，也不能通过 URL 或接口访问。
- 角色停用不会删除历史审计和审批任务。
- 权限变更写入前后 JSON、操作人和时间。

## 13. 主要风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 多角色并集导致范围扩大 | 授权保存前显示范围扩大提示，并提供生效权限预览 |
| 只隐藏前端菜单造成越权 | 所有后端接口统一执行菜单、操作和数据范围校验 |
| 部门名称变更导致范围失效 | 只保存飞书部门 ID，名称实时从组织架构读取 |
| 旧授权清理不完整 | 按迁移角色编码和旧权限表记录执行幂等清理，并保留旧表结构 |
| 最后管理员被移除 | 后端事务级保护最后一个系统管理员 |
| 审批待办被数据范围误过滤 | 审批任务按任务分配人查询，关联业务详情再做范围校验 |
| 客户供应商没有部门字段 | 按关联可见项目过滤，独立未关联主数据只向全部范围用户开放 |

1. 允许一个人绑定多个角色，支持“项目负责人 + 出纳”等复合岗位。
2. 首版开放本人、负责项目、本部门及下级、全部数据范围；暂不开放逐项目清单授权。

4. 保留环境变量系统管理员作为最高权限兜底，并在页面显示为不可移除的系统管理员。

## 15. 按钮权限设计

### 15.1 判断原则

所有会改变业务数据、暴露敏感数据、发起外部动作或产生经营结果的按钮，都使用独立的操作权限。查询、分页、TAB、关闭和返回等纯界面动作不单独配置权限。

权限判断顺序固定为：

```text
菜单 VIEW
  → 按钮 ACTION
  → 目标数据 DATA_SCOPE
  → 敏感字段 FIELD_POLICY
  → 执行接口并写审计
```

前端没有权限时隐藏按钮；有权限但当前数据不在范围内时不展示可操作按钮，后端接口统一返回 403。按钮是否显示不能作为唯一安全措施。

### 15.2 按钮显示规则

| 场景 | 处理方式 |
| --- | --- |
| 没有菜单 `VIEW` | 不显示菜单，直接访问路由返回 403 |
| 有 `VIEW`，没有按钮操作权限 | 隐藏按钮，列表和详情仍可查看 |
| 有操作权限，但目标记录超出数据范围 | 隐藏编辑/删除等按钮，接口返回 `DATA_SCOPE_REQUIRED` |
| 有权限但业务状态不允许操作 | 按钮保留但置灰，并显示状态原因 |
| 有权限且满足业务条件 | 正常显示并允许操作 |
| 系统管理员 | 显示所有按钮，但仍遵循状态机和二次确认 |

例如，用户有“项目合同查看”但没有“合同删除”，可以进入合同详情，但不显示删除按钮；用户有“合同删除”但该合同所属项目超出范围，仍不能删除。

### 15.5 特殊按钮规则

1. **保存按钮**：保存草稿使用 `CREATE` 或 `EDIT`，不能因为按钮文字是“保存”就绕过业务权限；合同“保存草稿”和“保存合同”共用合同新增/编辑权限，但分别受状态校验。
2. **审批按钮**：通过、驳回和冲销权限分开；合同收付款审批还必须满足当前用户是有效出纳审批人，工时审批必须满足当前用户是任务审批人。
3. **删除按钮**：删除前必须再次执行数据范围、状态机和关联数据校验。已审批收付款不显示删除，使用冲销按钮。
4. **导出按钮**：导出权限独立于查看权限；导出内容严格沿用当前筛选条件、数据范围和字段脱敏规则。
5. **附件按钮**：预览和下载需要资源查看权限；上传和删除需要资源编辑权限；审批人只读附件，不自动获得删除权限。
6. **同步和重试按钮**：组织同步、通知重试属于外部动作，需要单独操作权限并记录操作人、时间、结果和失败原因。
7. **快捷入口**：工作台快捷按钮只在用户同时拥有对应菜单查看和创建/审批权限时显示，点击后仍回到正式页面执行完整校验。

### 15.6 角色配置界面

角色详情中的权限树按“菜单 → 操作”两级展开：

```text
☑ 项目管理
  ☑ 查看
  ☑ 新增
  ☑ 编辑
  ☐ 删除
☑ 项目合同
  ☑ 查看
  ☑ 新增
  ☐ 编辑
  ☐ 删除
```

- 勾选菜单 `VIEW` 后才可勾选其业务操作。
- 取消 `VIEW` 时自动取消该菜单下所有操作。
- 勾选新增、编辑、删除、审批、导出、同步或配置时，界面提示对应影响范围。
- 父菜单显示半选状态表示只授权了部分子菜单。
- 角色保存前显示“新增权限、移除权限、扩大数据范围”的差异摘要。

### 15.7 生效权限接口返回

登录和管理员预览接口统一返回以下结构：

```json
{
  "menus": [
    {
      "code": "project",
      "actions": ["VIEW", "CREATE", "EDIT"],
      "scope": {"type": "OWNED_PROJECTS", "department_ids": []}
    }
  ],
  "field_policies": {"bank_account": "MASKED", "daily_cost": "VISIBLE"},
  "sources": ["项目负责人", "经营查看者"]
}
```

前端只根据 `menus[].actions` 控制显示；后端从同一个有效权限服务读取同样的结果，避免前后端各自维护一套权限判断。

## 16. 本次设计结论

可以为所有业务按钮增加权限，但不把每个视觉按钮都做成后台配置项。最终采用“菜单查看权限 + 业务操作权限 + 数据范围 + 固定字段保护”的四层模型，既能细化审批、删除、导出、附件和同步等高风险动作，也不会让查询、分页、关闭弹窗等基础交互变得难以维护。
