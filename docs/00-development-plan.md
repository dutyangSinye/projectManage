# 综合项目管理系统开发方案与计划

> 当前文档基线：v3.0.27 ｜ 对应生产运行版本：v3.0.26 ｜ 更新时间：2026-09-02

当前系统已从原始工时管理方案演进为“工作台、工时管理、项目管理、系统管理”四大模块的综合项目管理系统。历史规划中的真实飞书审批实例、审批回调、小时级工时和多维表持续回写没有作为当前生产核心能力；现行实现边界以 `docs/v3.0/27-current-baseline-v3.0.27.md` 为准。

## 1. 当前结论

系统建议采用“飞书负责身份与审批，工时系统负责业务数据、校验和报表”的架构：

- 用户身份、部门、直属上级来自飞书组织架构，不在系统内维护密码和独立账号。
- 工时申请/补录/撤回等审批动作通过飞书审批完成。
- 工时系统保存业务快照、审批实例号、审批状态和审计记录，用于查询、统计、锁账和追溯。
- 飞书多维表作为现有数据源或业务台账，通过适配器同步，不建议直接把多维表当作系统核心数据库。

当前无法完成你提供的多维表的字段级核对：打开链接后页面停留在飞书登录页。本文中的字段和规则因此分为“建议设计”和“待登录确认”两类，登录后应先完成数据字典确认，再进入开发。

登录后已完成实测，详见第 10 节。原先这句“无法完成字段级核对”仅保留为访问过程说明，不再作为当前阻塞项。

## 2. 目标范围

### MVP 必须包含

1. 飞书单点登录与组织架构同步。
2. 日/周工时录入、草稿保存、修改、删除和批量录入。
3. 项目、任务、工时类型、日期和工时数校验。
4. 提交飞书审批、查看审批进度、审批完成后回写工时状态。
5. 我的工时、团队工时、项目工时和月度汇总报表。
6. 管理员维护项目、工时规则、审批模板映射和结算周期。
7. 导出 Excel/CSV、审批异常重试、同步日志和审计日志。

### 建议放到 V2

- 项目预算与剩余工时。
- 工时成本金额和人员成本率。
- 自动提醒、逾期催办和异常工时识别。
- 移动端增强、跨天工时、批量导入历史数据。
- 多套审批模板、按部门/项目动态路由审批人。

## 3. 业务流程

```text
飞书登录
  -> 同步用户/部门/直属上级
  -> 用户填写工时草稿
  -> 系统校验并生成工时单
  -> 调用飞书审批创建审批实例
  -> 飞书审批人处理
  -> 审批回调或定时补偿查询
  -> 系统更新审批状态并锁定/释放工时
  -> 报表按已审批工时统计
```

关键原则：审批状态以飞书审批结果为准，系统本地状态用于查询和业务控制；回调必须幂等，不能因为重复回调产生重复工时或重复统计。

## 4. 飞书集成方案

### 4.1 身份与组织架构

- 创建飞书企业自建应用，配置网页应用回调地址。
- 使用飞书 OAuth/登录态识别当前用户，保存 `user_id`、`open_id`、`union_id` 中可用的稳定标识。
- 定时同步部门、用户、直属上级、在职状态；事件订阅用于缩短变更延迟。
- 本地用户表只保存飞书标识和必要的展示信息，不保存密码。
- 所有权限判断使用本地组织快照，避免每次报表查询都依赖飞书实时接口。

### 4.2 审批

建议先配置一套“工时申请/补录”飞书审批模板，系统通过审批 API 创建实例，并将以下信息写入审批表单：

- 申请人及部门。
- 工时周期、工时明细或明细摘要。
- 项目/任务、工时类型、工时数。
- 申请原因、补录原因、附件。
- 系统工时单号。

系统保存审批实例号和审批定义标识。审批回调处理通过事件类型、实例号和事件版本去重；回调失败时进入重试队列，并由定时任务调用审批查询接口补偿。

实测当前多维表的“审批”仍是自定义字段和消息通知链路：审批人通过飞书消息收到提醒，然后进入多维表处理；没有看到创建飞书审批实例、审批实例号或审批回调步骤。若“利用飞书审批”是硬性要求，开发时应把这套字段审批升级为真正的飞书审批实例，原有 `审批状态`、`审批人` 和通知字段只作为本地镜像与兼容历史数据使用。

### 4.3 多维表

登录后需要核对以下内容：

- 表名、视图名、实际字段名、字段类型和是否必填。
- 人员字段是飞书人员字段还是文本字段，是否能拿到人员唯一 ID。
- 日期/时间字段的时区和精度，工时是数字、时长还是公式字段。
- 项目、任务、部门是否通过关联字段/查找字段维护。
- 现有状态值、审批字段、公式字段和自动化规则。
- 是否存在历史数据，是否需要迁移，是否允许系统回写。
- 多维表的可见范围、管理员权限和 API 访问方式。

建议最终形成一份字段映射表：`多维表字段 -> 本地字段 -> 飞书审批字段 -> 报表字段`，并为每个字段记录转换规则、来源、是否可编辑和异常处理方式。

## 5. 建议数据模型

### 核心表

- `users`：飞书用户标识、姓名、部门、直属上级、在职状态、同步时间。
- `departments`：部门树、部门负责人、飞书部门标识。
- `projects`：项目编码、项目名称、负责人、状态、有效期。
- `tasks`：项目下任务、任务负责人、状态、可填工时范围。
- `worklogs`：人员、日期、项目、任务、工时类型、开始/结束时间、工时数、描述、来源。
- `timesheets`：一次提交的工时单，包含周期、总工时、状态、提交人和版本号。
- `approval_instances`：审批定义、审批实例号、工时单号、状态、创建/完成时间、原始摘要。
- `approval_events`：飞书回调事件 ID、事件版本、处理状态、重试次数和错误信息。
- `periods`：工时周期、截止时间、是否锁定、锁定人和锁定时间。
- `audit_logs`：关键操作、操作者、对象、旧值/新值、请求 ID和时间。

### 建议的工时状态

`DRAFT` 草稿、`SUBMITTED` 已提交、`APPROVING` 审批中、`APPROVED` 已通过、`REJECTED` 已拒绝、`WITHDRAWN` 已撤回、`LOCKED` 已结算锁定。

### 数据约束

- 同一人员、日期、项目、任务、工时类型的明细不能无提示重复。
- 每日工时上限、工作日规则、加班规则必须配置化，不写死在前端。
- 审批中和已通过的工时不可直接编辑；修改需撤回或发起补录流程。
- 已锁定周期不可修改，只能通过管理员解锁或冲正单处理。
- 报表默认只统计已通过/已锁定工时，草稿和审批中数据单独展示。

## 6. 技术架构建议

- 前端：Vue 3 + TypeScript + 企业内部管理台组件库。
- 后端：FastAPI + SQLAlchemy，提供 REST API 和飞书回调接口。
- 数据库：PostgreSQL；Redis 用于短期缓存、分布式锁和任务队列。
- 异步任务：组织架构同步、审批回调重试、定时补偿、提醒和报表汇总。
- 部署：Docker Compose 起步，生产环境使用 HTTPS、反向代理、独立数据库和日志采集。
- 集成层：封装 `FeishuDirectoryClient`、`FeishuApprovalClient`、`FeishuBitableClient`，业务层不直接拼接飞书 API。

当前目录里的 Python Flask 下载器与本系统无关，建议新建独立服务目录或独立仓库，避免复用现有配置和部署脚本。

## 7. 开发计划

### 阶段 0：需求和飞书环境确认（2-3 个工作日）

- 登录并完成多维表字段、视图、历史数据和权限盘点。
- 确认工时口径：正常工时、加班、请假、出差、跨天、节假日和补录。
- 确认审批模板、审批人规则、撤回/驳回/重新提交规则。
- 创建飞书应用，确认租户管理员、权限范围、回调域名和测试人员。

交付物：字段字典、业务规则、审批流程图、权限清单、接口清单和 MVP 验收标准。

### 阶段 1：基础工程与身份组织（4-5 个工作日）

- 项目脚手架、数据库迁移、配置管理和统一错误处理。
- 飞书登录、用户会话、权限中间件。
- 部门/用户首次全量同步、增量同步、手动重试和同步日志。

交付物：用户能通过飞书登录，管理员可看到组织架构同步结果。

### 阶段 2：工时录入和基础配置（5-7 个工作日）

- 项目、任务、工时类型、周期和规则管理。
- 工时单及明细的增删改查、草稿、批量录入。
- 前后端一致的工时校验、周期锁定和操作审计。

交付物：不接审批时，用户可以完整录入并查看自己的工时。

### 阶段 3：飞书审批闭环（5-7 个工作日）

- 审批模板配置和表单字段映射。
- 创建审批实例、查询审批状态、撤回和重新提交。
- 回调验签、幂等、重试、死信记录和定时补偿。
- 审批结果回写工时单，异常状态提供人工重试入口。

交付物：测试人员可完成“填写 -> 提交 -> 飞书审批 -> 回写 -> 锁定”的闭环。

### 阶段 4：报表与多维表同步（5-7 个工作日）

- 个人、部门、项目、周期四类报表。
- 按审批状态、工时类型、人员和项目筛选。
- Excel/CSV 导出和权限控制。
- 根据阶段 0 的映射表实现多维表导入/回写，保留源记录 ID和同步结果。

交付物：管理者可以按组织和项目核对工时，系统与多维表数据可追溯。

### 阶段 5：测试、上线和试运行（5-7 个工作日）

- 单元测试、接口测试、审批沙箱测试、权限测试和并发/重复回调测试。
- 迁移一小段历史数据进行核对。
- 灰度上线一个部门或项目，连续运行一个完整工时周期。
- 修复问题后扩大范围，补齐监控、备份、回滚和运维手册。

整体预计：2-3 人开发团队约 4-6 周；单人开发约 7-9 周，取决于飞书审批模板和多维表历史数据复杂度。

## 8. 验收标准

- 在职员工可通过飞书登录，离职/禁用用户不能新增工时。
- 组织架构变更在约定时间内同步，失败可重试且有日志。
- 工时数据可保存草稿，非法日期、超限工时和重复明细会被拦截。
- 每个已提交工时单都能关联唯一飞书审批实例号。
- 重复回调、网络重试不会产生重复记录或重复统计。
- 飞书审批通过/拒绝后，本地状态和报表在约定时间内一致。
- 已锁定周期不能被普通用户修改，所有管理员修改均有审计记录。
- 个人、部门、项目报表的数字可以追溯到明细和审批记录。
- 多维表同步失败不影响已保存的本地工时，恢复后可以补偿同步。

## 10. 已确认的多维表结构与现状

### 10.1 数据范围

- Base 名称：工时填报；当前表：工时填报；当前视图：全部记录。
- 工时填报表当前有 84 条记录。
- 项目数据源有 18 条项目记录。
- 部门对照表有 4 条映射记录。
- 工时分析仪表盘显示：总工时 166 天、填报人次 84、执行中项目 18、待审核记录 9、已通过记录 71。
- `71 + 9` 不等于 84，说明还有其他状态记录，或仪表盘组件存在筛选口径差异；系统开发时必须统一统计口径，不能只依赖仪表盘数字。

### 10.2 工时填报字段

| 字段 | 实测类型/来源 | 现有用途 |
| --- | --- | --- |
| 项目 | 单选，主字段 | 工时所属项目；由自动化从关联项目带入 |
| 关联项目 | 关联/查找字段 | 关联项目数据源 |
| 项目阶段 | 单选 | 需求、设计、开发、联调、测试、交付、现场、管理、其它 |
| 工时类型 | 单选 | 项目工时、管理工时、其它工时 |
| 开始时间、结束时间 | 日期 | 计算工作日工时 |
| 工作描述 | 文本 | 工作内容说明 |
| 提交人 | 飞书人员 | 记录填报人 |
| 二级部门 | 部门字段，来源于提交人 | 自动取得填报人的部门 |
| 一级部门 | 文本 | 由部门对照自动化补填 |
| 状态 | 单选 | 本地、出差、休假、异地办公 |
| 填报日期 | 日期 | 填报日期 |
| 审批状态 | 单选 | 待审核、已通过、已驳回 |
| 审核意见 | 文本 | 审批意见 |
| 工时核算 | 公式，整数 | `NETWORKDAYS([开始时间],[结束时间])` |
| 项目负责人、审批人 | 飞书人员 | 项目负责人和当前审批人 |
| 是否自审 | 公式 | `IF([提交人]=[审批人],"是","否")` |
| 审批通知状态、结果通知状态 | 单选 | 未通知、已通知、通知失败 |
| 审批通知时间、结果通知时间 | 日期时间 | 通知时间记录 |
| 通知错误 | 文本 | 自动化失败信息 |
| 父记录 | 关联/查找字段 | 父子记录关系，需确认是否参与业务汇总 |

时间字段当前按日期使用，`NETWORKDAYS` 只按工作日计算，没有看到法定节假日配置。因此现有“工时”本质是工作日天数，不是小时数；如果产品目标是小时级工时，必须改为开始/结束日期时间或增加“实际工时/小时数”字段。

### 10.3 项目数据源

项目数据源字段已确认如下：

- 项目名称：文本主字段。
- 项目编码：文本，已有部分编码为空或使用 `/`，需要在新系统中增加唯一性校验。
- 项目负责人：飞书人员。
- 工时审批人：飞书人员。
- 主管领导：飞书人员。
- 所属部门、项目状态：单选字段。
- 是否可填报：布尔/待办型字段，用于控制项目是否允许新增工时。

样例项目包括“机器人集群智能调度管理系统”“自动化钢筋加工产线”“建筑物流搬运机器人研发与应用”等，项目数据源应作为独立的项目主数据表迁移，而不是把项目名称复制到工时表中维护。

### 10.4 部门对照表

当前映射包含产品研发部下的信息化中心、应用创新中心、技术研发中心，以及技术服务部下的技术服务部。现有方案是先通过飞书人员字段得到二级部门，再用对照表补出一级部门。

建议新系统直接使用飞书组织架构的部门树生成一级/二级部门，部门对照表仅作为历史兼容和人工覆盖配置，不再作为组织架构的唯一来源。

### 10.5 已配置的 7 条自动化流程

1. `工时填报 - 催填`：定时向指定人员或群组发送催填消息。
2. `填报通知`：定时向指定人员或群组发送填报通知。
3. `部门自动化填入`：当二级部门不为空且一级部门为空时，在部门对照表按二级部门查找并回写一级部门。
4. `查找审批人并更新审批人字段`：新增工时且关联项目不为空时，在项目数据源按项目名称查找，回写项目负责人、工时审批人、项目状态和项目字段，并将审批状态设为待审核。
5. `判断为非自审批的审批人通知`：审批状态为待审核、是否自审不为是且审批人不为空时，向审批人发送包含提交人、项目、阶段、时间、工时和描述的飞书消息，并将审批通知状态设为已通知。
6. `判断为自审批变更为主管领导的审批人通知`：是否自审变为是时，按关联项目查找主管领导并把审批人替换为主管领导。
7. `审批通过通知提交人`：审批状态变为已通过时，先将结果通知状态设为已通知，再向提交人发送审批通过消息。

自动化中心显示 7 条流程全部启用，但同时提示企业内自动化流程本月运行次数已用尽。现有流程还存在多次修改触发、通知状态先写成功再发送消息等一致性风险，不能作为新系统的核心业务引擎。

## 11. 基于实测结果的方案调整

1. **审批必须独立改造**：新系统创建真实飞书审批实例，使用审批实例号关联本地工时单；不再依赖“进入多维表处理”的消息作为审批凭证。
2. **小时/天口径必须先定**：当前公式是工作日天数。若要管理研发人员每日投入，建议使用 `work_hours` 数字字段，日期只负责归属，开始/结束时间作为可选明细。
3. **项目主数据先行**：先同步项目数据源，校验项目编码、项目负责人、审批人、主管领导和是否可填报，再开放工时录入。
4. **人员部门从飞书同步**：二级部门和一级部门由组织架构快照生成；对照表作为历史数据修正表。
5. **通知改为服务端可靠任务**：通知发送、审批回调、失败重试和结果回写放入任务队列，保留通知日志和幂等键。
6. **报表按审批状态统计**：默认只统计已通过/已锁定工时；待审核、已驳回和未通知数量单独显示，并对账多维表的 84 条记录。

### 调整后的优先级

- P0：飞书应用权限、真实审批模板、工时单位、审批人规则、项目可填报规则。
- P1：用户/部门同步、项目主数据同步、工时录入、审批实例闭环、个人/部门/项目报表。
- P2：催填、通知、历史多维表回写、项目预算、成本金额和异常分析。

基于本次实测，阶段 0 的“表字段盘点”已完成；下一步应先完成飞书应用和审批模板确认，再开始阶段 1 的工程实现。
