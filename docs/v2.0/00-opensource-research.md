# 芯烨工时管理系统重设计依据

> 版本：v2.0 ｜ 日期：2026-08-25 ｜ 状态：已确认，已实现

## 1. 重设计结论

本次不再把真实飞书审批 API 作为核心链路。飞书继续承担组织架构来源和消息通知渠道，工时审批状态、审批意见、审计记录由芯烨工时管理系统本地维护。

```text
填报一条具体工作内容
        ↓ 默认保存并提交
生成一条本地审批任务
        ↓ 飞书机器人通知项目审批人
审批人进入系统
        ↓ 通过 / 驳回
工时单状态更新并留下审计记录
```

## 2. 对既有多维表方案的取舍

| 既有能力 | v2.0 处理 | 原因 |
|---|---|---|
| 项目、人员、部门字段 | 保留并迁移为本地主数据 | 支撑项目填报和权限校验 |
| 按周期合并工时后审批 | 移除 | 不同工作内容可能对应不同审批人和处理意见 |
| 飞书审批实例、回调、撤回 | 暂不接入 | HTTPS、模板配置、回调验签和状态补偿会放大部署风险 |
| 飞书机器人/应用消息 | 保留 | 只负责提醒，不承担审批权威状态 |
| 周期字段 | 保留为筛选、月度汇总、锁账维度 | 周期仍有报表价值，但不再是审批边界 |
| 多维表审批状态字段 | 作为历史导入字段保留 | 不再直接驱动新系统审批 |

## 3. 参考与自研判断

- 不引入第三方工作流引擎。当前审批只有单人通过/驳回、催办、审计和通知，采用本地状态机更容易部署和排查。
- 继续使用 Vue 3 + TypeScript、FastAPI + SQLAlchemy、Docker Compose，与现有部署保持一致。
- 采用飞书 `open_id` 或本地用户 ID 识别审批人，姓名只作为展示快照，不能作为授权条件。
- 采用通知适配器封装飞书群机器人 Webhook 和飞书应用消息 API，先支持配置可用的通知方式，未来可替换而不改审批业务。

## 4. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 通知发送失败导致审批人不知道 | 审批任务仍保留在系统；记录通知状态；支持重试和催办 |
| 审批权威从飞书迁移到本地 | 详情页和审计记录完整保留；报表只统计本地已通过/已锁定数据 |
| 旧周期单与新单模型不一致 | 升级时逐条拆分旧周期明细为独立审批任务，旧单仅作历史兼容 |
| 审批人仅有姓名 | 项目配置改为关联本地用户，要求存在 `open_id` 或本地绑定身份 |
