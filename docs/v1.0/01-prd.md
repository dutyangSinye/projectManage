# 芯烨工时管理系统产品需求文档

> 版本：v1.0.1 ｜ 日期：2026-08-25 ｜ 状态：已修订

## 1. 背景与目标

### 一句话概述

一个以飞书组织架构为用户基础、以飞书审批为审批入口、以本地数据库承载工时业务和报表的企业工时管理系统。

### 目标用户

- 员工：按项目和阶段填报工时、提交审批、查看历史记录。
- 项目负责人/审批人：查看待审工时、处理异常、追踪项目投入。
- 部门负责人：查看部门投入、人员负荷和审批积压。
- 管理员：维护项目、规则、周期、权限和集成配置。
- 财务/经营管理人员：按项目、部门、阶段导出已审批工时。

### 核心问题

当前多维表通过字段和自动化流程完成工时登记，但存在以下问题：

1. 审批是消息提醒，不是真实飞书审批实例，难以追踪完整审批链。
2. 自动化受运行次数限制，失败后缺少可靠重试和补偿。
3. `NETWORKDAYS` 只计算工作日天数，不能表达小时级投入和节假日规则。
4. 项目、部门、审批人依靠多个字段和自动化拼接，数据一致性不足。
5. 仪表盘指标与原始记录数存在口径差异，无法形成稳定的经营报表。

### 成功指标

- 100% 登录用户来自飞书组织架构，不维护本地密码。
- 每一笔提交的工时都有唯一本地工时单号和飞书审批实例号。
- 审批回调重复、乱序或失败重试不会生成重复工时。
- 已审批报表可以追溯到工时明细和审批记录。
- 试运行一个完整工时周期后，系统与人工核对结果的差异为 0。
- P0 主流程“登录 -> 填报 -> 提交审批 -> 审批完成 -> 报表”完成率达到 99%。

## 2. 用户场景

| 场景 | 触发 | 用户操作 | 期望结果 |
|------|------|----------|----------|
| 日常填报 | 员工完成项目工作 | 选择项目、阶段、日期和工时，填写描述并保存 | 获得草稿，可继续修改 |
| 周期提交 | 周期截止前 | 选择周期内草稿，检查汇总后提交 | 生成唯一工时单并跳转飞书审批 |
| 审批处理 | 审批人收到飞书审批 | 在飞书完成通过/驳回 | 系统状态同步，报表口径更新 |
| 管理分析 | 例会或月结 | 按部门、项目、阶段和人员筛选 | 查看已审批投入并导出明细 |
| 历史迁移 | 系统首次上线 | 导入多维表历史记录并核对 | 历史数据可查询，不改变原始记录 |

## 3. 功能清单

| 编号 | 功能 | 优先级 | 描述 | 验收标准 |
|------|------|--------|------|----------|
| F1 | 飞书登录 | P0 | OAuth 登录，绑定飞书用户标识 | 无本地密码；未授权用户不能进入系统 |
| F2 | 组织架构同步 | P0 | 同步用户、部门、直属上级和在职状态 | 全量/增量同步可重试，有同步日志 |
| F3 | 项目主数据 | P0 | 同步或维护项目编码、负责人、审批人、主管领导和可填报状态 | 不可填报项目不能新增工时 |
| F4 | 工时录入 | P0 | 草稿、批量录入、编辑、删除、复制上一条 | 前后端校验一致，重复提交不产生重复记录 |
| F5 | 周期提交 | P0 | 按周期汇总草稿并生成工时单 | 工时单有版本、总量和明细快照 |
| F6 | 飞书审批 | P0 | 创建审批实例、接收回调、同步结果 | 每个工时单唯一关联审批实例 |
| F7 | 状态与锁账 | P0 | 草稿、审批中、通过、驳回、撤回、锁定 | 通过/锁定数据不可普通修改 |
| F8 | 个人/管理报表 | P0 | 个人、部门、项目、阶段和审批积压 | 默认只统计通过/锁定数据，可下钻明细 |
| F9 | 导入与兼容同步 | P1 | 导入现有多维表，过渡期可回写状态 | 原记录 ID 可追溯，失败可补偿 |
| F10 | 通知与催办 | P1 | 飞书消息通知、逾期提醒和失败重试 | 消息发送幂等，有失败记录 |
| F11 | 项目预算 | P2 | 预算、实际投入和剩余量 | 本期不作为上线阻塞 |
| F12 | 成本金额 | P2 | 人员成本率和项目成本 | 本期不作为上线阻塞 |

## 4. 明确不做的范围

- 不在本系统内维护飞书用户密码、独立账号和组织架构主数据。
- 不复制实现完整的审批引擎，审批流转由飞书审批完成。
- 不把多维表继续作为核心事务数据库。
- 不在 MVP 中实现薪资、绩效、考勤打卡、请假审批和费用报销。
- 不在 MVP 中实现复杂项目预算、成本核算和自动排班。

## 5. 关键业务规则

### 数据规则

- 工时归属到具体人员、项目、阶段、工时类型和周期。
- 项目必须处于可填报状态，且项目负责人、审批人信息有效。
- 用户、部门、直属上级以飞书同步快照为准；历史工时保留当时的部门快照。
- 系统支持 `DAY` 和 `HOUR` 两种单位，但租户在 MVP 阶段只能选择一种主单位。默认兼容现有数据使用 `DAY`。
- 历史多维表的 `NETWORKDAYS` 结果导入为 `DAY` 单位，不反推小时。

### 审批规则

- 每个周期提交生成一个工时单，工时单包含明细快照。
- 系统创建真实飞书审批实例，保存审批定义编码和审批实例号。
- 审批通过后工时单进入 `APPROVED`；驳回进入 `REJECTED`；审批中禁止修改。
- 修改已通过工时必须发起补录/更正单，不能覆盖原记录。
- 自动审批人规则：优先使用项目工时审批人；若提交人与审批人相同，则切换为项目主管领导；仍无审批人时阻止提交。

### 报表规则

- 默认统计 `APPROVED` 和 `LOCKED` 工时。
- `PENDING`、`REJECTED` 和通知失败单独计数，不混入已审批投入。
- 每个指标必须标注单位、时间范围、状态口径和最后更新时间。
- 报表数据必须可下钻到工时明细、工时单和飞书审批实例。

## 6. 依赖与风险

| 风险 | 影响 | 对策 |
|------|------|------|
| 飞书应用权限或审批权限未开通 | 无法登录/创建审批 | 阶段 0 完成租户管理员确认和沙箱验证 |
| 审批模板字段与工时单不匹配 | 审批无法创建或回写 | 先冻结审批表单字段映射，再开发 |
| 工时单位未确定 | 报表和历史数据口径不一致 | MVP 默认 DAY，同时保留单位字段和转换层 |
| 组织架构变更导致历史部门漂移 | 历史报表失真 | 保存组织快照，不只保存当前部门 |
| 多维表自动化额度/失败 | 过渡期数据不一致 | 本地任务队列和可补偿同步，不依赖自动化 |
