# 芯烨工时管理系统调研与设计依据

> 版本：v1.0.1 ｜ 日期：2026-08-25 ｜ 状态：已修订

## 1. 调研范围

本阶段以用户提供的飞书多维表和当前工作区为主要事实来源，确认现有业务结构、字段、自动化和数据风险。当前工作区只有一个与工时系统无关的 Flask 下载工具，没有可复用的工时业务代码，因此新系统采用独立服务目录/独立仓库设计。

## 2. 已确认的现有系统

- 工时填报表：84 条记录。
- 项目数据源：18 个项目，包含项目编码、项目负责人、工时审批人、主管领导、所属部门、项目状态和是否可填报。
- 部门对照表：4 条一级/二级部门映射。
- 工时计算公式：`NETWORKDAYS([开始时间],[结束时间])`，当前口径是工作日天数。
- 审批状态：待审核、已通过、已驳回。
- 当前审批链路：字段状态 + 飞书消息通知 + 多维表自动化，并非真实飞书审批实例。
- 已配置自动化：7 条，均启用；飞书提示本月自动化运行次数已用尽。

## 3. 复用与自研决策

| 能力 | 决策 | 原因 |
|------|------|------|
| 身份认证 | 使用飞书 OAuth/登录能力 | 用户体系已经由飞书组织架构维护，不重复建设账号密码 |
| 审批 | 使用飞书审批 API 和审批事件 | 满足“利用飞书审批”的硬性要求，避免把消息通知当审批凭证 |
| 组织架构 | 使用飞书组织架构 API + 本地快照 | 报表和权限查询不能依赖每次实时请求，需保留部门历史 |
| 项目主数据 | 本地项目主数据 + 多维表导入/同步适配器 | 项目编码、状态、可填报等规则需要稳定约束 |
| 工时主数据 | 自研本地数据库 | 需要版本、锁账、审计、幂等和审批状态机 |
| 报表 | 自研查询与汇总 | 统一审批口径，解决现有仪表盘指标与记录数不一致 |
| 自动化通知 | 自研任务队列，飞书消息作为通道 | 避免受多维表自动化次数限制影响，提供失败重试 |

## 4. 技术选型依据

采用 Vue 3 + TypeScript、FastAPI、PostgreSQL、Redis 和 Docker，理由是团队可快速交付管理台、接口契约清晰、关系数据适合审批和报表、异步任务容易拆分。暂不引入低代码工时引擎或大型工作流平台，审批编排交给飞书，业务状态和数据一致性由本系统控制。

## 5. 结论

不直接迁移现有多维表的自动化逻辑。迁移数据和字段含义，重建“本地工时单 -> 飞书审批实例 -> 回调更新 -> 报表统计”的核心链路。现有多维表保留为历史兼容、人工核对和过渡期回写目标。
